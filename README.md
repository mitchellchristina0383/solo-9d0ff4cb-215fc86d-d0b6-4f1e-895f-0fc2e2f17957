# 磁带机取回模拟器（tape-drive-sim）

用 FastAPI 模拟一台磁带机：接收待取文件清单和副本目录（至多 12 卷），
给出**装带 + 回卷总次数最少**的读取顺序；值班员逐步回报读带结果，
系统按带头新位置重排剩余文件，并列出已无副本可读的文件。

## 运行

```bash
docker compose up --build      # 服务监听 8000 端口
# 浏览器打开 http://127.0.0.1:8000/docs （Swagger UI）逐步操作
```

本地开发（无 Docker 时）：

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/uvicorn app.main:app --port 8000
.venv/bin/pytest tests/ -q                    # 单元/集成测试
.venv/bin/python scripts/walkthrough.py       # 对运行中的服务走一遍完整取回流程
```

## 实现

### 代价模型（与值班室约定）

- **装带**：挂载一卷计 1 次；当前已挂载的卷继续读不计；装带后带头在卷首。
- **读带**：只能向序号增大方向读；同卷内按序号升序读不需要回卷。
- **回卷**：在当前卷上需要读比带头位置更小的序号时，回卷 1 次（回到卷首再升序读）。
  因此每卷至多回卷 1 次，且只有“当前已挂载卷”可能被迫回卷。

### 规划算法（`app/planner.py`）

卷数 ≤ 12，**精确枚举**所有非空卷子集（≤ 4095 个）：

1. 子集须覆盖全部待取文件（每文件至少一个可用副本落在子集内）；
2. 代价 = 装带数 + 回卷数。装带数 = 子集卷数（当前卷在子集内则减 1）；
   回卷 = 1 当且仅当某文件在子集内的副本**全部**落在当前卷且全部低于带头；
3. 取代价最小者；平局依次按装带更少、用卷更少、位掩码更小裁决（确定性）；
4. 副本指派：优先非当前卷的副本，其次当前卷带头之后的副本，最后才回卷读；
   读取顺序：当前卷最先（避免卸下再装），卷内升序，当前卷低于带头的部分
   排在回卷动作之后。

### 交互协议（`app/main.py` / `app/state.py`）

| 接口 | 说明 |
| --- | --- |
| `POST /jobs` | 创建取回作业（文件清单 + 副本目录），返回初始状态与最优计划；每次创建分配递增的 `job_id`，并覆盖旧作业 |
| `GET /plan` | 按当前带头位置重算最优计划，`next_step` 即下一步要回报的读带步骤；响应带 `job_id` |
| `POST /receipts` | 回报**当前计划第一步**的读带结果（`ok` / `failed`），须携带 `job_id`，返回重排后的计划 |
| `GET /state` | 当前作业 id、当前卷、带头位置、待取/已取/无副本文件、停用副本、累计执行次数 |
| `DELETE /job` | 作废当前作业 |

回执入账规则（核对作业、确认首步、入账、重排在同一把锁内一次生效）：

- **回执必须携带所属作业的 `job_id`**：作业被替换后旧 `job_id` 的回执返回 409（附当前
  `current_job_id`）；作业被删除后返回 404。迟到回执绝不推进新作业，即使两个作业的首步
  （file/volume/position）完全相同。
- **同一读带步骤只入账一次**：已出现在历史中的步骤再次回报（无论结果）返回 409，
  带头、取回进度、副本启用状态、计数、历史全部保持原样。
- **只用当前计划第一步的新回执更新进度**：不符的回执返回 409 并附上期望步骤，状态不变；
  计划已无可回报步骤时同样返回 409。
- **响应快照在锁内凝固**：创建作业与每张生效回执的响应，其状态与计划都取自本次操作刚完成
  那一刻的同一进度（不可变 `JobSnapshot`）；并发交错时先入账的响应不会混入后一步的进度。
- **失败也推进带头**：成功或失败，带头都推进到该步骤的卷内序号（跨卷步骤视为装带已发生）；
- **停用出错副本**：失败副本立即从目录中停用，不再参与后续规划；
- **每步重排**：每张回执生效后按新带头位置重新规划，响应中列出已无副本可读的文件。

  坏副本停用并重排、两次失败的完整流程（含无副本清单、累计计数、计划清空后再回报 409）、
  实际流程永不回卷的不变式、入参校验（>12 卷 / 未知文件 / 重复副本 / 非法序号）、
  无作业时 404，以及本次修复新增：
  - `test_late_receipt_after_job_replacement_is_rejected`：同清单覆盖作业后，旧 job_id 的
    迟到回执 409，新作业的带头、进度、副本、计数、历史全部不变；
  - `test_late_receipt_after_job_delete_is_rejected`：删除后旧回执 404，重建后旧 id 仍 409；
  - `test_duplicate_receipt_for_same_step_is_rejected`：同步骤重复回执 409，失败的重复回报
    不会停用副本，计数与历史不增加；
  - `test_response_snapshot_is_consistent_after_commit`：生效回执响应中的状态与计划同属本次
    入账后的进度，后续提交不改写已返回的快照；
  - `test_concurrent_receipts_each_response_reflects_its_own_commit`：真实 uvicorn 上并发
    交错两张回执，逐张校验 200 响应的状态/计划自洽（先入账响应不含后一步进度），被拒回执
    无副作用（连续 12 次运行无抖动）。
- 结果：`21 passed`。
- 走查：`scripts/walkthrough.py` 对运行中的服务完整走了一遍取回流程
  （与 /docs 页面调用同一套 API）：初始计划 2 装带 0 回卷 → 乱序回报被拒（409）→
  覆盖作业后旧 job_id 的迟到回报被拒（409）→
  A 的两个副本先后读失败（带头推进、副本停用、每步重排）→ A 进入无副本清单 →
  B/C/D/E/F 全部取回 → 同步骤重复回报被拒（409），累计装带 3 次、回卷 0 次。
- 本环境无 Docker 守护进程，`docker compose up` 未在本机执行；
  Dockerfile / docker-compose.yml 已做静态检查（YAML 合法、端口与健康检查一致、
  依赖与测试环境一致），运行期行为以本地 uvicorn + 上述走查与并发测试验证。
  有 Docker 的环境按“运行”一节 `docker compose up --build` 后在
  http://127.0.0.1:8000/docs 即可复走全部步骤（回执 JSON 需带 `job_id`）。

## 遗留事项

1. **实际流程中回卷永不触发**：计划按升序调度且失败副本即停用，
   “当前卷上存在带头之下的可用副本”这一回卷前提在回执流中不可达
   （不变式见 `test_live_flow_never_needs_rewind` 注释）。
   回卷分支仅为理论完备性保留（如初始状态允许带内定位、或未来支持指定初始卷）。
2. **状态仅存内存**：单作业、重启即丢；作业以递增 `job_id` 标识，覆盖/删除后的迟到回执
   会被拒绝，但重启后 id 计数从 1 重新开始。如需多作业并行或持久化，要引入存储层。
3. **装带/回卷视为必然成功**：真实驱动器可能有机械故障，模型未覆盖。
4. **同位置多副本**：允许不同文件登记相同 (卷, 序号)，视为先后可读（带头语义为
   “最后读到的序号”，同序号可连续读）；如需严格物理语义可改为带头 = 序号 + 1。
5. **无鉴权**：默认内网值班室使用；对外暴露需自行加认证。
